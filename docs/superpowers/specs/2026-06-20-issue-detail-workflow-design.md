# 问题详情页工作流重组设计

Date: 2026-06-20
Status: Draft for review

## Goal

将 `apps/web` 的问题详情页从“模块堆叠”重组为“排障工作流”。页面打开后，用户应先完成快速判断，再顺着证据链查看问题成因，最后在处置区完成指派、记录、修复标记和高级分组操作。

本次设计只重排前端信息架构与文案，不引入新的后端接口或数据模型。

## Current Pain Points

- 处理动作、证据内容和辅助信息是平铺展示的，用户需要自己判断先看什么。
- 合并、拆分这类高级操作和常规 triage 处在同一视觉层级，容易显得割裂。
- SDK 信号、Breadcrumbs、调用栈、环境上下文和关联性能都很有价值，但没有形成一条清晰的证据叙事。
- 评论模块的文案偏“讨论”，更像聊天区，不像问题处置记录。

## Design Principles

1. 顶部先回答“这是不是一个需要立刻处理的问题”。
2. 主栏先回答“问题是如何发生的”。
3. 右栏先回答“接下来该做什么”。
4. 合并、拆分只在确认证据后出现，视觉上要弱于常规 triage 动作。
5. 继续沿用当前深色专业风格，不改产品主题，只改信息组织方式。

## Information Architecture

### 1. Header: Judgment Layer

首屏顶部保留问题标题、指纹、状态和严重级别，并强化判断所需的信号：

- 事件数、影响用户数
- 首次出现、最近出现
- 回放入口
- 关联性能风险入口或提示

这一层的目标是让用户在 5 秒内知道“要不要处理、谁在处理、影响有多大”。

### 2. Main Column: Evidence Chain

主栏按时间和证据优先级排列，建议顺序为：

1. 事件时间线
2. 调用栈
3. Breadcrumbs
4. SDK 信号
5. 环境上下文
6. 维度分布
7. 关联性能

这里的逻辑不是“功能模块都展示出来”，而是让用户从事件样本一路往前追到用户行为、运行环境和性能背景。

### 3. Right Rail: Triage Actions

右侧固定为处置区，包含：

- 状态切换
- 负责人指派
- 修复版本标记
- 排查记录
- AI 辅助分析
- 高级操作

状态、负责人和修复版本属于常规动作，应始终可见。合并和拆分属于高级操作，放在处置区底部，视觉上降权。

## Component Changes

### Workflow Panel

将现有“处理状态”区拆成更清晰的两层：

- `状态与负责人`
  - 状态按钮
  - 负责人下拉
  - 保存负责人按钮
- `修复标记`
  - 修复版本输入
  - 标记已修复按钮
  - 当前负责人、修复于、解决时间、回归信息保持在同一块内

这样可以让“先指派、再记录、再标记修复”的动作顺序更自然。

### Comments Panel

将“讨论”更名为“排查记录”或“处理记录”，文案上从聊天语义转向工作记录语义。

这一块应强调：

- 记录排查假设
- 记录修复结论
- 保留交接信息

### Manual Grouping Panel

将“Manual grouping”改为更明确的高级操作区，建议标题偏向：

- 高级操作
- 问题归并
- 归并与拆分

默认不要把它放在首屏最显眼位置。它应该像“确认证据后才会使用的工具”，而不是 triage 主流程的一部分。

### SDK Signals

SDK 信号区保持在详情页内，但从“散落的附加信息”变成“证据链补充”。

建议继续按类别分组：

- Trace context
- HTTP breadcrumbs
- Console breadcrumbs
- Route breadcrumbs
- User interaction breadcrumbs

如果有 trace id、HTTP breadcrumb、路由跳转或交互事件，应让用户一眼看出“这条错误是怎么发生的”。

### Related Performance

关联性能不应只作为补充卡片。它要在证据链里承担“同时间窗、同设备、同会话是否存在性能劣化”的作用。

## Copy And Localization

本次重组需要同步统一中英文文案，避免页面里出现“讨论 / Manual grouping / target issue id”这类语义割裂的混杂表达。

建议统一原则：

- triage 相关模块使用“处理 / 排查 / 处置”语义
- 辅助信息使用“证据 / 上下文 / 信号”语义
- 高级操作使用“归并 / 拆分 / 归类”语义

## Data Flow And Constraints

- 不新增后端接口。
- 不改变现有 issue、events、comments、facets、related performance、AI analysis 的数据来源。
- 只调整页面上的分组、顺序、标题和局部文案。
- 空状态、加载态和错误态保持现有行为，只是放到更合理的位置。

## Testing Strategy

验证这次重组时，重点看三件事：

1. 页面在中文环境下不再混入英文操作标题。
2. 首屏能清楚看到判断信息和处置入口。
3. 证据链从时间线到 SDK 信号再到关联性能是连贯的，而不是被多个同级面板打断。

建议验证方式：

- `bun test apps/web/src/lib/i18n.test.ts`
- `cd apps/web && bun run lint`
- `cd apps/web && bun run build`
- 浏览器手动检查问题详情页的首屏、右栏、证据链和高级操作区

## Non-Goals

- 不改 API 层。
- 不改数据库结构。
- 不新增新的 triage 状态机。
- 不做大范围视觉换肤。
